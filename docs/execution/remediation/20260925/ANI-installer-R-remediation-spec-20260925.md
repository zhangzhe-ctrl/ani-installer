# ANI installer：R 系列复审整改执行细则

## 1. 任务性质、依据与完成边界

本文件与同目录的 `ANI-installer-R-remediation-goal-20260925.txt` 共同定义本轮整改。目标是修复实际产品代码及其测试，不是再做一次只有文档的审查，也不是启动新一轮全量 R 系列或 B 系列建设。

依据为随附 `ANI-installer-main-audit-20260925.md` 中 F01–F12、§4 小回归和原复现证据。审查源码基线为 `f58430e84a1949b837c59139dc45979c33ae5c4f`，不是对执行时最新 main 状态的保证。先比较当前源码；问题已被修复的，补证据并验证不回归，不重复改写。报告中的推断和摘取代码复现允许质疑，但必须给出生产调用链、实际命令及针对同一条件的反证。

以下“应当”“必须”是本轮提出的整改和验收要求，不是声称产品已经具备这些能力。原报告的绿色 CI、选定组合通过、隔离摘取函数测试，均不能作为本轮修复提交通过的证据。证据包中的 `review_regression_test.go.example` 未在完整仓库编译，必须先按实际接口适配；不能把 `go fmt` 当编译、把负向案例的 bug_observed 当功能验收通过。

保留已经明确的产品范围：KubeKey 为现有安装后端；代码发布物与材料发布物独立；主 CNI 二选一；存储与业务组件按配置选择；KCN 依赖的专属 Envoy 留在 KCN 组合，不改成公共业务网关；不部署 B 系列新组件来解决本轮测试依赖。

不轮换当前实验口令，不输出、提交或打包秘密。不升级 Kubernetes/组件/工具版本或放宽批准摘要来消除失败。不引入自动接管、自动升级、清盘、自愈、复杂迁移兼容系统或通用工作流引擎。已有严格 YAML、Ceph 显式开关/逐节点设备声明/默认类保护、多命令错误传播等整改不能回退。

## 2. 执行约束与证据方法

先读仓库相关 `AGENTS.md`、现有 `docs/execution/progress.yaml`、`docs/execution/status-decision.md`、当前相关代码和本任务包，记录工作目录、分支、HEAD、未提交修改与可用工具链。保留他人改动，不自动 reset/clean。历史对照使用固定提交的隔离 worktree/fixture，不把生产工作树回退到旧版。

每个问题至少形成一条可追踪链：原生产路径下的特定错误输入或行为 → 对应修复 → 同一测试通过 → 正向功能仍可用。测试失败必须命中目标缺陷；编译失败、未装依赖或 fixture 错误不算缺陷复现。已修复问题可用历史对照加当前回归说明。

允许 fake kubectl、Helm、systemctl、SSH/API 和临时 registry 来控制输入、计数和故障；不允许替换掉被审查的实际 checker、重新实现业务函数或仅 grep 注释证明合同成立。真实脚本的启动、分支、资源选择和退出路径必须进入测试。离线测试必须隔离 HOME、kubeconfig、路径、端口和临时资源，设置误触真实集群的拦截。不能执行真实删除来验证“只会删除一次”。

本轮默认先完成代码、隔离测试和构建。复用用户明确且仍有效的目标/授权，已有参数不重复询问；旧安装报告、历史路径、口令可用不等于本轮实机授权。未授权时不恢复 ESXi 快照、不重启机器、不清缓存、不运行真实破坏性验收。实机条件不满足只阻塞对应验收，不停止其余代码工作。push、合并 main、发布正式产物也按明确授权处理；没有推送权限就交付本地 diff/提交与命令，不宣称 CI 已通过。

六组工作可按依赖调整顺序，状态、身份、锁等最小共用定义先统一。每组同步补测试，不等最后一次性补门禁。不要求每个小修复都重装三台机器；局部测试后再跑统一门禁，最后运行受影响的授权实机组合。

## 3. 第一组：真实验证路径、一次性变更和取消（F01、F09）

### 3.1 需要检查和修改的入口

以 `kubekey/pkg/ani/verify.go`、`kubekey/scripts/verify.sh`、`kubekey/builtin/core/roles/ani/metrics/{tasks,templates}/` 为主，同时检查 Fluent Bit 和所有已实现组件的安装后验证入口。必要修改落到 `pkg/connector` 及实际 subprocess 调用层。改动必须覆盖首装、组件新增、CLI 验证和保留的 legacy wrapper，不能只修新命令而留旧入口旁路。

### 3.2 smoke 与 acceptance 的边界

首装/新增安装后只做必要的就绪与轻量功能检查。smoke 不删除或重启既有组件服务 Pod，不修改全局通知路由/静默，不删除历史 attempt 的资源。可以使用本 attempt 独占的临时探针和命名隔离的数据；报告必须如实说明这种受控写入，不称为绝对只读。探针需要唯一 attempt 标识，清理只允许当前 attempt 自己创建、已记录 UID 的资源，不凭通用 label 清扫所有历史资源。

完整 firing/resolved 通知链、Prometheus 数据、Alertmanager 静默持久化、其他已有业务级持久化验证保留，迁入显式 acceptance 或相应受授权验证层。不得把“拆分”实现为删掉测试步骤或将必需检查全部 skipped。未实现的专项必须明确 not_implemented/not_verified，不写成该能力通过。

移除调用者先 delete 后 helper 超时再 delete 的第二次重建，以及其他隐式修 CNI/重启 agent/重进重建的分支。一个目标失败，停止后续变更并收集只读证据；诊断失败不覆盖原始失败。

### 3.3 至多一次的目标变更

目标必须由声明和现场共同确定：namespace、控制器 kind/name/UID、Pod 名/UID、容器、PVC UID、实际挂载与 PV 绑定。删除前复核目标仍为授权对象，并用 UID 前置条件或等价条件变更方式防止同名替换后误删；宽泛 label selector 不是授权边界。

在固定 canonical 状态目录内，以安装 run/验收目标为键，在同一产品锁下先持久记录意图和旧身份，再发变更。状态不由输出目录决定。并发、进程崩溃和更改 `--output` 都不能重新获得同一目标的删除额度。对已发送但结果不明的动作保持 unknown，先只读核实，不自动重放。不要承诺网络故障下不可证明的 exactly-once；实现的是授权范围内至多一次发起和对不确定结果的保守处理。

不同声明目标可分别合法验收，不应被一个过粗的“本 run 已有结果文件”阻挡。结果导出/重复读取允许发生，但不能因此重复变更。等待目标 Ready 与业务就绪；仅 Running 不够。

### 3.4 真正的数据语义

PostgreSQL：在隔离测试表/键中写入唯一内容并提交，确认重建前可查询；一次授权重建后通过真实 SQL/鉴权读回同一内容，不能靠 PVC 上 marker 文件冒充数据库持久化。

NATS：使用现有批准工具/协议创建隔离 JetStream 测试流、持久消息和必要消费者，记录发布确认及序列；重建后读取原消息并验证声明的消费/确认行为。不要把文件能 cat、普通 pub/sub 或健康接口等同于 JetStream 持久化。

两者均校验声明的 controller/PVC/PV/挂载身份保留，并输出旧新 Pod UID。测试结果不能被新建一份同名数据、换 PVC 或启动了不 Ready 的服务冒充。测试工具缺材料时登记材料缺项，不在离线节点在线安装依赖。

### 3.5 截止时间与远端未知

把 ctx 和阶段截止时间传到真实脚本、子进程及必要 API。请求有单次超时，循环有总预算；不能通过无限重试或延长超时掩盖故障。子进程派生的本任务进程必须有界退出，不能仅父 bash 退出而后代继续写入。只结束本任务进程组/SSH会话，不能 pkill 系统共享进程或关闭其他任务的共享连接。

SSH/远端变更取消后无法证明远端已停止，保持 remote_result_unknown，并将语义传到父安装记录与报告；本地超时不是远端回滚。专项失败不改变成功首装的历史结果。

## 4. 第二组：新增组件的现场身份、所有权及执行边界（F02、F03、F08）

### 4.1 生产入口

主要修改 `pkg/ani/components_install.go`、`builtin/core/playbooks/ani_components.yaml` 和涉及所有权、路径、Helm 执行的角色。计划检查与 execute 检查必须共用规则，不再靠注释保证执行安全。

共享首装、组件 execute 和有变更验收的产品互斥机制。按当前拓扑，可以要求这些变更只在原安装节点执行并使用固定本地锁；不因此扩大成分布式锁系统。需验证实际运行主机，不能只相信配置写了 installerNode。锁只能保护遵守本安装器协议的执行；仍需在资源变更点使用避免覆盖已有对象的操作，不能把锁宣称为能阻止外部运维变化。

### 4.2 基础身份和健康

成功首装记录提供集群稳定身份（例如 kube-system UID 结合受管安装记录）、实际节点集合/身份、主 CNI、版本、registry 与存储等必要不变量。新增执行时实读并比对，还要确认节点 Ready、相应 CNI 工作负载健康及存储能力满足实际所选组件。

原配置摘要与新配置摘要分别记录；比较不可变底座字段，而非要求整个新旧配置摘要相等。状态时间戳、resourceVersion 等自然变化不作为永久身份。业务 Namespace UID 仅“读到并记下”不算确认原集群。StorageClass 按每个实际 PVC 的最终有效选择检查，不能只看全局默认。

`--kubeconfig` 必须落实到生产子进程 kubectl/Helm 和相应执行主机，计划检查的集群就是写入的集群。隔离继承的 HOME/KUBECONFIG 漂移；默认 admin.conf 与显式覆盖路径均有可验证的目标绑定。连接失败、Forbidden、无效输出不是 NotFound。

### 4.3 计划不可代替写入前检查

严格解析计划 schema、runID、状态、摘要和组件条目，验证路径安全并重新计算规范 --only/依赖闭包。未知、禁用、暂缓、重复、越界组件或不合法状态一律拒绝，不能静默丢弃后报告成功。需要的依赖应与原配置声明一致，不暗改用户配置。

在产品锁内、首次业务/集群变更前重新检查：成功底座、集群身份/健康、当前 owner/revision/版本、材料身份、代码身份和作用域。相关条件自计划后改变就要求重新计划；不得拿旧 planned 状态直接写入。人工可读计划摘要并不是签名，不要仅靠可重算配置摘要阻止计划范围被改写。

### 4.4 所有权与 no-op

读取当前实际 release 修订和部署状态，不能固定读 v1，也不能忽略 failed/pending 的最新修订而挑历史 deployed 记录当健康现状。名字、Chart 名/版本相同不构成 ANI 所有权证据。对新增受管 Helm/manifest 资源写入可追溯归属，关联安装记录；受影响的共享 CRD/集群级资源同样有冲突检查。

自有、同版本/所需配置一致且健康的对象只读返回 already_installed；全部均已存在时返回 no-op 成功结果，不重新执行 role。外部同名、所有权缺失、版本变化、failed/pending、不明状态要拒绝，不通过改 label、补 annotation 或 `--force` 自动接管。当前模式只做新增，不因 role 的 `helm upgrade --install` 把竞态变成升级；使用不会隐式升级已有 release 的新增路径。

遗留对象无法证明归属时明确拒绝，不伪造旧所有权记录。没有真实成功记录的旧实验底座需要在授权实验流程内准备，不能用 validate 的产物冒充。

### 4.5 作用域和记录

组件新增不导入 create_cluster、不执行 kubeadm/CNI/Ceph/registry 生命周期，不修改无关 release。新增工作目录、日志和 connection fragment 独立，路径从一个受控运行上下文传给角色，禁止写回 base 的 connections.d 再事后读取“补救”。原首装 run/state/connections 保留。

新记录区分计划目标、实际执行、already_installed、失败及未运行，并关联原 run；不能把新配置全部 enabled 组件直接宣称为已安装。部分失败仍保存已发生动作和后续 not_run，不能只留下空结果。文件存在性导致的二次启动拒绝，也必须发生在改写运行文件之前。

## 5. 第三组：成功安装记录和真正前置的校验（F04、F05）

### 5.1 状态与成功记录

主要修改 `pkg/ani/runner.go`、`preflight.go`、`run_manifest.go` 和验证/新增消费者。区分配置校验报告、执行状态、成功安装记录。可以复用现有结构并增加最小类型/结果字段，不要求引入新的数据库或复杂状态机。

最后完成阶段和最终结果分开。配置、材料、安装、连接事实生成、状态落盘等失败和取消均准确记录；远端结果未知不得改写为普通确定失败或成功。持久写入失败不能静默忽略后报成功。保留原始失败和失败阶段；结果文件对读者不可半写，关键意图在业务变更前持久化。

首装完整成功后，产品自动生成 run.json、状态、实际身份和连接事实，并打印准确路径。配置 validate 和组件 plan 均不产生“安装成功”的声明。首装得到的成功记录就是后续 --base-run 的来源，不另造手工模板、修改状态或者依赖未来 B 任务准备底座。

保留既有 profile 语义：profile=base 不包含存储/业务组件；本轮选定集成验收可用 profile=full 配置所需底座、关闭稍后待新增的组件，不要求把 profile=base 改成 full 来绕过不变量。

代码提交、源码树指纹、实际二进制摘要、规范化站点摘要、材料锁摘要分别记录真实来源。不得把 package.yaml 摘要当 site 摘要，更不能当源码指纹。新 runID 应独立于仅配置摘要，避免两次相同配置执行被错误当同一次安装。

### 5.2 消费者和坏输入

成功验收/新增组件必须检查有效成功记录及匹配状态，核对 schema、runID、摘要、集群身份和必要物料身份。缺状态、半写、畸形、空/短摘要、旧 schema 缺必要证据、失败、中间状态、远端未知、同集群名不同实际集群、record/state 不匹配，均应明确报错且不变更。

只读诊断可以保留查看失败现场的能力，但不能将其输出成“成功安装验收”。专项验证结果独立于首装结果，不能把 acceptance fail 回写成“首装从未成功”，也不能用成功首装掩盖专项失败。

### 5.3 实际预检

统一 required/材料校验清单和调用，不保留构造却未被消费的 required 列表。核对本次所选能力需要的非空归档、二进制可执行性、批准 Chart 内容、ISO及记录、镜像表/锁一致性、完整校验和和必要离线渲染。

`CheckUnitInactive` 必须实际查询，分别处理 active、inactive、not-found、查询错误。不存在可进入新装；已有外部同名 unit 即使 inactive 也不能等导入镜像后再拒绝，更不能自动 stop/disable/rewrite。专门测试生产默认 nil-runner 分支不是空函数。

首次远程/业务变更或不可复用运行目录创建前完成可在本地确定的检查。允许固定锁、独立 preflight 报告、可清理的隔离临时目录/验证缓存；“零业务变更”不等于绝对不写任何字节。坏输入修正后无需恢复三台机器即可重试；已经改变机器的失败则不能当干净重试自动继续。

ISO记录/锁格式不符、必需条目缺失或读取失败必须失败，不能 len不符就跳过。大文件摘要宜流式处理，不能因一次性读入导致不必要内存占用。磁盘空间检查针对实际写入文件系统。保留 Ceph 逐节点显式设备与默认类保护，探测错误不能当空盘，绝不加入清盘步骤。

## 6. 第四组：材料的精确绑定与全链路验证（F06）

主要修改 `pkg/ani/materials.go`、`scripts/build-offline.sh` 和首装/新增材料校验。尽量共用现有结构化 lock API；脚本需要信息可调用同一实现导出结构化条目，避免另写第三套 grep/awk 审批规则。

Chart 以具体条目的 name/version/artifactPath/hash 精确配对，并核对实际 Chart metadata。其他条目中的合法摘要不能为本条目背书。复制前后/落盘产物检查对应内容，损坏或错配不得通过。不能从待验文件本身重算“批准摘要”；随材料附带的锁若缺少独立批准来源绑定，不能宣称具备独立真实性保证。不要求扩展完整签名平台，但必须复用现有批准来源，并把缺口写明。

默认镜像收集与传入现成 HAULER_ARCHIVE/STORE 的入口使用一致的内容验证标准。按批准 digest 收集或在发布前核对实际摘要；tag和镜像数量正确不够。核对实际仓库/ref/重写映射，禁止凭 original 字符串猜本地路径。自研注入归档保留批准归档及转换链，不编造 source index。

OCI index 继续定位本次所选平台的子 manifest，核对其实际字节摘要及引用的 config/layers；闭包完整且内容与批准链一致。对发布归档中的内容做实际验证，不以层路径存在或HTTP200冒充已验证完整归档。内容校验可流式、按已验证内容身份缓存，不能因优化退回名字/大小/数量判定。首装和新增复用一致校验，不把新增降级为HEAD200。

KubeKey嵌套artifact里的ISO按准确目标路径和内容摘要校验；同名不同内容、含糊/重复目标不能当“已有无需处理”。不能外部ISO正确、内部发给节点的ISO错误仍通过。批准来源不齐的必要base材料单独登记阻塞，不能暗改锁通过；不要求为未启用B组件补全部材料。

所有外网材料准备留在既有批准构建/材料流程，安装节点不联网拉缺失镜像、Chart、包和工具。坏包必须在制包发布前或可证明的前置阶段失败，不能把检查成功单纯延后到修改机器之后。

## 7. 第五组：渲染语义和独立发布使用（F07、F12）

主要修改 `pkg/ani/config.go`、ANI CLI、嵌入项目处理、相关发布脚本。render与执行共享有效配置选择，明确base/full和KCN/KubeOVN关系；不因修渲染把KCN专属Envoy抽成业务公共网关。

渲染使用相同已批准离线Helm、真实Chart、values及必要API版本上下文，包含hooks/CRDs和相关connection模板。Operator在运行期生成的资源/镜像应明确由声明和必要验证覆盖，不声称helm template已生成所有动态对象；不因此新建通用Operator模拟器。

按文件/嵌入片段实际语言检查YAML、Python和shell，合法PY_EOF不误当YAML；不是把所有非EOF heredoc都跳过。Kubernetes YAML语法错误必须报出来源/文档位置。识别同一文件内及跨文件的重复资源。运行时字段按具体允许字段绑定/模拟或记录延迟验证；出现.item/.stdout不能豁免其他缺值。供应商材料有明确身份、来源和必要字段级例外，不能靠*-install.yaml后缀整文件放行。

默认资源来自本次代码发布物的嵌入或随包受校验资源；不得要求artifact带源码树。子kk默认当前os.Executable解析的可执行文件，显式--kk/--project-addr属于覆盖路径，需记录并核对适用身份，不能静默执行另一套旧代码。有效kubeconfig贯穿实际命令。

发布物迁移到无Git/无源码目录后，从不同工作目录执行。PATH中没有kk或有诱饵旧kk也不能选错。测试输入/输出/项目路径安全，拒绝越界和不支持的路径形态必须在业务变更前。不要为路径适配重新合并代码包和材料包。

## 8. 第六组：实际门禁、冷启动证据与文档（F10、F11）

保留一个 `scripts/check-code.sh`，CI和build调用同一门禁。保留有效历史检查，增加普通/builtin实际产品构建、受影响包的vet和测试、pkg/connector回归、真实checker轨迹、真实离线Chart渲染与CLI发布隔离测试。工具链遵循当前go.mod及批准环境，不降版本、不在断网门禁中自动下载工具链；Python模块等依赖前置检测。

参考命令在 `kubekey/` 执行；按实际可用包路径与构建标签核实后纳入唯一门禁，而不是复制后假定已运行：

```bash
GOTOOLCHAIN=local go build ./...
GOTOOLCHAIN=local go build -tags builtin ./...
GOTOOLCHAIN=local go vet ./pkg/ani/... ./pkg/connector/...
GOTOOLCHAIN=local go vet -tags builtin ./pkg/ani/... ./pkg/connector/... ./cmd/kk/app/...
GOTOOLCHAIN=local go test -count=1 ./pkg/ani/... ./pkg/connector/...
GOTOOLCHAIN=local go test -count=1 -tags builtin ./pkg/ani/... ./pkg/connector/... ./cmd/kk/app/...
```

不能只调用LIB_ONLY定义helper就声称完整smoke路径无变更；测试应覆盖正式dispatcher→真实checker→外部命令边界。取消/并发相关包可补有针对性的race测试，不能以要求全上游所有测试为由阻塞必要回归。

workflow paths包含根run_on_node.sh、restore_esxi_snapshots.sh、config/**、门禁和实际依赖输入。历史负面对照固定旧提交，不依赖HEAD还是坏版本。缺工具/必要测试材料导致非零和准确原因，不能skip后汇总全绿；fixture与真实材料测试分开标识。

冷启动必须读取结构化证据，核对schema、主机、unit、registry/材料身份、不同新旧bootID、当前运行匹配及真实冷拉结果。空文件、无关对象、旧证据或内容缺项保持not_verified/明确失败；is-enabled/is-active只证明配置和当前服务状态。systemctl真实输出解析也应用代表性fixture测试。没有授权不自动重启或清理镜像；只在真实验证后才写verified。

复用现有进度文件，新增一份当前整改交付摘要和必要证据即可；不新建平行状态系统或数十份重复卡片。保留原历史结果，新增修复提交的结论，不把旧的selected pass修改成“所有组合通过”。

## 10. 授权实机回归：最小选定组合

不是必须重跑全部历史场景。代码和所需本地门禁通过、授权与批准材料齐备后，在原授权实验节点上执行受影响的选定组合。不得因“缺底座”人工生成run.json或跳过新增校验。

先形成一份明确运行输入：授权目标、将发生的动作、站点配置、代码/材料摘要、验收目标、保存证据位置。测试用profile=full启用本轮所需底座和原选定服务，关闭一个稍后要新增的既有组件。优先复用原KCN/Ceph/Loki组合和新增Valkey案例；换案例必须记录原因，不能用替代案例证明未测组件通过。

流程：按授权实验流程准备干净机器 → 真实离线首装 → 由产品自动产出成功run/state → 实际smoke → 新配置生成计划 → execute新增关闭的那个组件 → 再计划/执行同版本组件证明只读no-op → 对明确授权目标执行一次专项并核对真实业务数据。无需人工修JSON、补owner或复制旧连接片段。

证明计划及新增没有通过本次命令改变既有底座和未选组件：保留命令轨迹，比较必要UID、镜像/版本、受管配置与原run/连接事实摘要。不以自然变化的resourceVersion、时间戳当永恒不变量；出现自发重建也要记录，不能既忽略事故又声称一切未变化。

断网安装要有实际隔离证据；阶段耗时、exit code、第一失败点、相关UID和日志保存完整。失败不得临时手修CNI、重复删Pod或重写材料摘要后接着报“原尝试通过”。保留失败现场，在授权范围内修代码/准备材料后另开可追踪新尝试，禁止同参数盲目循环重装。

KubeOVN全链、OpenSearch、外部存储类、cold-registry等未执行的矩阵仍标not_verified；本轮局部相关代码测试必须做，但不把未测实机组合签成通过。冷启动需要额外明确重启/冷拉授权，不能通过删现有镜像缓存制造实验条件；可按批准实验设计使用无缓存客户端。无该授权则完成证据校验代码/回归并保留live pending，不据此停止其他修复。

## 11. 交付物和退出标准
