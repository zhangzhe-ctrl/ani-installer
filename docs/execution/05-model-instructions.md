# 05｜交给快速执行模型的规则、提示词和回报

本文件不是新的Agent服务。它只是每次任务的固定上下文。把本文件与当前一张任务卡交给模型，避免它在长聊天、旧文档和多份release中自行“整理出新架构”。

## 1. 每次输入的最小集合

提供本规则、蓝图§1–5、当前卡、已完成前置的task-result，以及卡里明确的源码文件。不要要求模型重新读整个历史网页；R00已做冲突裁决。也不要让模型为了实现一个组件重搜并更新全部版本。

一张R卡较大时使用R07.1/2/3、R15.1/2/3。组件卡一次只运行一个M/I/T/V阶段；复杂卡如KFP一次只实现它的一个子场景。完成当前范围后停止，不自动接下一张卡。

## 2. 通用提示词（可直接复制，填写大写占位项）

```text
你在维护既有ANI installer，而不是设计新安装器。
本次只执行 TASK_ID，当前阶段 STAGE，允许文件以任务卡为准。
输入源码目录：REPO。计划目录：PLAN。证据目录：EVIDENCE。
先只读确认源码指纹、工作目录与前置任务结果；HEAD相同不等于工作树相同。
已提供的15项审查使用A编号，实施使用R/B编号，历史实验A19等不要混入。

必须遵守：
1. 保留KubeKey fork、Go入口和固定role，不创建另一套框架。
2. kk与artifact独立；纯代码修改只构建code release，材料变化才制包。
3. kcn专属Envoy绝不供其他业务复用，也不改造成通用入口。
4. LWS/vCluster/GPU/业务Envoy暂缓；Istio/Knative默认不装。缺依赖时明确报错，不能解除暂缓。
5. 目标只有172.16.101.20–22。编译/测试在ssh fedora。当前阶段没有明确写权限时，不连接目标执行变更。
6. 不清OVN/LSP、不wipe磁盘、不删PVC/CRD、不重启CNI/OVS、不追加修复式Pod重建。
7. 先新增或运行能够真正执行行为的负向用例，再修实现；关键词存在与零测试通过不算验证。
8. 文档拟新增的命令/测试/检查器必须先实现并检查实际存在；不能编造运行结果。
9. 官方版本材料不能核实则blocked，禁止用latest/master/别版本SHA填空；只核对本卡的固定版本。
10. 遇到不属于本卡的问题，只记录新问题与证据，不顺手跨文件重构。
11. 禁止自动git reset/clean/stash/commit/push和对外发布。
12. 实机失败先取证并停止；快照只由授权lab流程在修正版局部测试通过后执行，不进入installer。

执行顺序：
A. 报出当前任务、前置证据、计划修改文件和本次是否可能写集群。
B. 对照当前源码定位任务卡问题，若已修复，提供具体测试而不是重复修改。
C. 先复现/测试，再最小修改，再重复同一测试；记录真实命令和退出码。
D. 只在当前卡授权且所有门禁满足时，执行该卡的实机阶段。
E. 按templates/task-result.yaml报告，未执行项not_run；不要接着执行下一张卡。
```

## 3. 可直接用的首次指令

```text
本次只执行R00，不编译、不安装、不还原快照。
读取01蓝图§1–5和tasks/R00.md。
确认本地权威源码和Fedora唯一源码/发布目录；记录HEAD与treeSHA。
核对旧AGENTS与后续kcn供料记录，按实际材料状态写冲突裁决。
把旧“解耦kcn Envoy”标为已撤销。HAProxy/kube-vip仅当前未使用材料，不启用。
输出R00 task-result和下一张建议任务R01，然后停止。
```

R00任务的“建立编译环境”不表示本次自动安装工具。缺工具记录确切版本/路径，由受控准备步骤解决。

## 4. 一个整改任务的指令示例

```text
本次只执行R02。前置R00、R01结果随附。
先定位metrics/fluent-bit中失败后反复重建与重启kcn CNI/OVS的路径，
写mock命令轨迹测试，证明组件不Ready时当前脚本会越界。
仅删除正式安装/verify路径中的恢复绕过；保留将来专项中的一次计划内重建。
顶层验证首失败后只做只读取证，后续变更检查not_run。
不修改kcn镜像、Envoy、Ceph、网络参数，不接入新组件，不启动三节点实验。
交付实际diff、负向回归日志和task-result，然后停止。
```

## 5. 一个组件阶段的指令示例

```text
本次只执行B02.M。不要实现或安装Milvus。
读取B02.md，固定Milvus2.6.24/Chart5.0.25/专用etcd/RocksMQ/RGW路线。
取得该版本真实官方Chart及递归子Chart，列出应用覆盖字段、静态/动态/验证镜像。
把pymilvus SDK、wheel和验证工具也列为材料；SDK版本不得凭服务器版本猜。
验证归档与摘要，写values-contract.md和material-report；未核实条目保持blocked。
不调整基础Kubernetes/Rook版本，不换MinIO，不恢复快照、不向目标机传大包。
交付B02.M结果后停止；只有负责人分配B02.I时才实现。
```

## 6. 人工如何审查模型是否完成

先看diff范围，再看实际测试输出，不先看模型结论。R卡要有原错误用例在修复后通过的证据；M卡要有可核实材料与摘要；I卡要有可编译/可渲染实现；T卡要有真正执行的各分支；V卡要有当前run而非旧日志。

检查六个常见偷换：把旧记录当本轮通过；把Pod Ready当读写正确；把字符串contains当真实API调用；把同名Pod当未重建/已恢复而不看UID；把临时手工修补当installer已修；把缺依赖跳过当成功。

模型因为缺权限、工具或材料而停下，要求它留下精确blocker和下一条只读排查命令。**不要要求它“无论如何继续直到绿色”**，那会鼓励绕过边界。

## 7. 每张卡结束的文字摘要格式

```text
任务：Rxx / Bxx.STAGE
源码：HEAD + treeSHA（不是只给分支名）
修改：允许范围内的实际文件
验证：真实执行命令、用例数、退出码、证据文件
状态：code / material / local / smoke / persistence / clean-offline / ANI分别列
现场：是否开始变更，是否出现结果未知，是否保留证据
阻塞：没有就写none；有就写具体对象/错误，不空泛写环境问题
下一步：建议哪一张卡，但没有自动执行
```

使用机器可读task-result时，字段必须真实，不把命令字符串预填为“已经运行”。计划只负责约束任务，不能替代执行结果。
