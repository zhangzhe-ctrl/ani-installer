### L-06 rules that were announced before they were enforced

The closeout was re-audited instead of being read back from its own ledger: 6 read-only lenses,
each reported blocker re-checked by two adversarial votes (default: refute if it cannot be
reproduced). Outcome 4 confirmed / 2 rejected, and the confirmed ones were fixed here:

1. **Record kind was a bare string comparison.** Editing `"recordKind"` to `install-success` in a
   landed record skipped every base-bytes / evidence-digest / live-cluster-uid check **and** re-keyed
   the one-shot pod-delete quota to the record's own sub-run — i.e. an observation record could re-arm
   a spent budget. Dispatch is now structural (the presence of `componentsExecution`), and
   `ValidateSuccessRecord` refuses such a record on the write side too (`--base-run`).
2. **A run that mutated the cluster but failed connection aggregation wrote no record at all** —
   the original L-06 symptom, on a failure path. Both cluster-touching failures now write a
   `result=failed` record, and a record-write failure is reported instead of swallowed.
3. **`metrics` was bound to StatefulSet `ani-metrics-prometheus` while its role creates
   `prometheus-ani-metrics-prometheus`.** A uid read of a workload that never exists degrades the
   target to `unknown`, so the pass either exits non-zero *after* installing with no record, or lands
   a record its own consumer refuses. Names are now checked against what each role rolls out.
4. **`TestComponentsExecutionRecordMixedScope` was named in three records but did not exist**
   (`go test -run <missing name>` returns PASS, so no gate catches it). It exists now.

Also tightened in this round, each with a test: the two scope lists must equal the record's own
targets; record-supplied `runId`/component names must be single path elements (a component name was
being concatenated into the verify script path and the evidence directory); a succeeded record must
carry plan + execute-report evidence (deleting `evidence` used to void every re-hash); an empty
scope can no longer be reported as `overall: pass`; the writer refuses to land a record its consumer
must reject (unchanged config digest); the read-only pass now honours the same plan-bound binary
check as the add pass; and the "quota cannot be re-armed" property is proven through `RunVerify`
(ledger file key = **base** run id) rather than by calling the ledger claim directly.

Rejected after attempts to refute (kept so they are not re-litigated): the claim that a missing
`status-decision.md` section would mislead readers (facts true, causality not — that section now
exists), and the claim that `| tail`-derived rc labels invalidate L-06 (the labels are indeed not
exit-code evidence; the L-06 rc values come from redirected runs with `$?`/`${PIPESTATUS[0]}`).

## 5. Incidents and self-reported deviations

* **Out-of-scope acceptance, with a real consequence.** To test "the quota cannot be re-armed", a step I
  added to my own script ran `kk ani verify --level acceptance --only postgresql --allow-pod-recreate`
  against the **base** record. That target had never been claimed on this base, so the product honestly
  performed its one declared recreation: pod `e49193ed-e8ac-4dee-b9a4-64dd4ca1020c` → `8ef12297-dbc7-467c-afd4-64f226a90a14`,
  PVC uid `1a338992-6587-4d5d-9b36-a07da21afae2` and PV unchanged, marker row read back, base smoke 6/6
  afterwards. **This was not authorized** (authorization stopped at valkey no-op → record → smoke), so:
  the postgresql budget on base `090732` is **spent** and must be reported as `quota_spent` by any later
  round; the step was removed from the `live-12`/`live-13` chains; it is recorded here and in
  `evidence/REVIEW-20260926/live-l11-acceptance-incident.sanitized.out`, and is **not** presented as an
  authorized acceptance. A repeat claim was then refused by the product itself
  (`already recorded as done`) with no further delete — which is the second, independent piece of evidence
  for the non-re-arming property.
* **Fluent Bit smoke flaked once, then passed on re-run.** At 21:39:55–21:42:16 a base smoke reported
  `fluent-bit: fail` (`rc 1`); a single-component re-run at 21:44 (`rc 0`) and a full base smoke at
  21:45:53–21:49:31 (6/6, `rc 0`) both passed, as did the earlier 21:33 base smoke. Evidence: all three log markers were
  found in Loki with correct `namespace/pod/container/node` labels, yet the metadata-check step's output
  file was 0 bytes and the report carried no failure detail. A shared, fixed-name client pod
  (`ani-fluent-bit-verify-client`, created by delete-then-run) is the prime suspect, but **the root cause
  is not established** and nothing was changed to mask it. This is a pre-existing observability robustness
  issue, not part of L-06, and it is deliberately left open.
* **Stale lab lock.** The previous round's lease was orphaned: the `flock`-holding shell was dead while its
  child `sleep infinity` still held fd 3 of the lab lock and would never release it. Terminated with
  explicit user authorization; every step this round holds the lock inside a single command so it is
  released on exit. A pid file is not proof of holding a lock.
* **Two benign operator mistakes retained as evidence:** one node payload executed locally by mistake
  (no `kubectl`, rc 127, zero side effects) and one read-only probe run outside the lock. Original outputs
  kept off-repo.
* **Base hygiene note:** the only non-running pod on the base is `ani-installer-smoke/ani-smoke-backend`
  in `phase=Failed`, left by the *first install's* own smoke at `09:13:36Z`. Removing it is a mutation and
  was not authorized; it is flagged for the round that owns smoke-resource cleanup.

## 6. Reproducing from a clone

```bash
git clone -b review/installer-f-remediation-20260926 <repo-url> && cd ani-installer/kubekey
go build ./... && go vet ./pkg/ani/
go test ./pkg/ani -count=1
bash scripts/check-code.sh            # the same entry point GitHub Actions runs
```

`check-code.sh` also runs the Python behaviour suites under `kubekey/scripts/test-*.py`. It requires a Go
toolchain that satisfies `go.mod` (`go 1.25.0` today) and **never downloads one** — an older toolchain fails
the gate by design rather than being silently fetched; this cycle the gate ran on `go1.26.7`. Neither `go test` nor the gate needs any binary
material, so they do run on a bare clone.

What a bare clone **cannot** do is offline packaging: `kubekey/scripts/build-offline.sh` calls
`materials place-charts --charts-dir kubekey/ani/charts` and has no fetch step, so the six Helm chart
archives (≈1.3 MB, largest 876 KB), the repository ISO and the image archive must be staged by whoever
builds the artifact. Those inputs are excluded by `.gitignore` (`*.tgz` and friends) — pre-existing
rules, unchanged here — so they are deliberately **not** in this branch, and `kubekey/ani/images.tsv`
plus `kubekey/ani/components.lock.yaml` (which *are* tracked) are the source-side records that pin them.
Live steps are likewise not reproducible from a clone: they need the three VMs, a built artifact package
and the site configs, none of which is in this branch.

## 7. Secrets and materials policy

No credentials, kubeconfigs, private keys, tokens, passwords, lab `.env` files or site configs with real
secrets are in this commit: the candidate set was scanned for the literal lab passwords (by value, without
echoing them) and for key/token shapes, and the sanitized evidence files were re-scanned after redaction.
Node addresses and pod CIDRs are replaced with `<LAB-MGMT-IP>` / `<LAB-POD-IP>` / `<SERVICE-CIDR-IP>`
placeholders in the committed excerpts; host names `node1..node3` are kept because they already appear in
the design docs. Two helper scripts at the repository root (`run_on_node.sh`,
`restore_esxi_snapshots.sh`) reference credential **file paths** and read them at runtime — they contain no
credential values. Nothing from `kubekey/build/`, `kubekey/_output/`, artifact stores, Hauler stores, image
archives, ISOs or material-preservation directories is tracked (`.gitignore` covers them and the staged set
was checked). Lab passwords were **not** rotated, since rotating them is not part of this review and would
invalidate the recorded evidence trail.
