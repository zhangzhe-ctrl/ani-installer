### L-06 rules that were announced before they were enforced

The closeout was re-audited instead of being read back from its own ledger: 6 read-only lenses,
each reported blocker re-checked by two adversarial votes (default: refute if it cannot be
reproduced). Outcome 4 confirmed / 2 rejected, and the confirmed ones were fixed here:

1. **Record kind was a bare string comparison.** Editing `"recordKind"` to `install-success` in a
   landed record skipped every base-bytes / evidence-digest / live-cluster-uid check **and** re-keyed
   the one-shot pod-delete quota to the record's own sub-run — i.e. an observation record could re-arm
   a spent budget. Dispatch is still *selected* by `recordKind`, but it can no longer be spoofed by that
   string: any record carrying a `componentsExecution` block that declares `install-success` is refused on
   the verify side, and `ValidateSuccessRecord` refuses the same shape as a `--base-run` anchor for a later
   addition.
2. **A run that mutated the cluster but failed connection aggregation wrote no record at all** —
   the original L-06 symptom, on a failure path. Both cluster-touching failures now write a
   `result=failed` record, and a record-write failure is reported instead of swallowed (stderr on the two
   failure paths, an error return on the two success paths — those reporting branches are not exercised by
   any test yet, and are listed under known gaps).
3. **`metrics` was bound to StatefulSet `ani-metrics-prometheus` while its role creates
   `prometheus-ani-metrics-prometheus`.** A uid read of a workload that never exists degrades the
   target to `unknown`, so the pass either exits non-zero *after* installing with no record, or lands
   a record its own consumer refuses. Names are now checked against what each role rolls out.
4. **`TestComponentsExecutionRecordMixedScope` was named in three records but did not exist**
   (`go test -run <missing name>` returns PASS, so no gate catches it). It exists now.

Also tightened in this round (each with a test except where marked): the two scope lists must equal the record's own
targets; record-supplied `runId`/component names must be single path elements (a component name was
being concatenated into the verify script path and the evidence directory); a succeeded record must
carry plan + execute-report evidence (deleting `evidence` used to void every re-hash); an empty
scope can no longer be reported as `overall: pass` (**enforced in `verifyScope`, but no behaviour test pins
that refusal branch yet**); the writer refuses to land a record its consumer
must reject (unchanged config digest); the read-only pass now honours the same plan-bound binary
check as the add pass; and the "quota cannot be re-armed" property is proven through `RunVerify`
(ledger file key = **base** run id) rather than by calling the ledger claim directly.

Rejected after attempts to refute (kept so they are not re-litigated): the claim that a missing
`status-decision.md` section would mislead readers (facts true, causality not — that section now
exists), and the claim that `| tail`-derived rc labels invalidate L-06 (the labels are indeed not
exit-code evidence; the L-06 rc values come from redirected runs with `$?`/`${PIPESTATUS[0]}`).

## 6. Reproducing from a clone

```bash
git clone -b review/installer-f-remediation-20260926 <repo-url> && cd ani-installer/kubekey
go build ./... && go vet ./pkg/ani/
go test ./pkg/ani -count=1
bash scripts/check-code.sh            # the same entry point GitHub Actions runs
```

`check-code.sh` also runs the Python behaviour suites under `kubekey/scripts/test-*.py`. It requires a Go
toolchain that satisfies `go.mod` (`go 1.25.0` today) and **never downloads one** — an older toolchain fails
the gate by design rather than being silently fetched; this cycle the gate ran on `go1.26.7`. Neither needs the cluster.

What a bare clone **cannot** do is offline packaging: `kubekey/scripts/build-offline.sh` calls
`materials place-charts --charts-dir kubekey/ani/charts` and has no fetch step, so the six Helm chart
archives (≈1.3 MB, largest 876 KB), the repository ISO and the image archive must be staged by whoever
builds the artifact. Those inputs are excluded by `.gitignore` (`*.tgz` and friends) — pre-existing
rules, unchanged here, and the baseline `f58430e` tracked no chart file either — and `ani/components.lock.yaml`
pins each one by `chartSource` URL plus `chartSha256`, so they are **downloaded material, not repo content**.

the gate is green on a tree where the chart archives have been staged (which is the author's tree, and the
one that produced `live-11/12/13`), and red on a bare clone for this one material-dependent test. Every
release whose digests §2 lists was built through the full gate with charts present, so those identities are
sound — but GitHub CI on this branch is expected to fail this same test, and that failure is a property of
the candidate, not of the reviewer's machine.

Deliberately **not** "fixed" here, because both available quick fixes would be dishonest in different ways:
committing the chart tarballs would upload third-party artifact material that the lock defines as a
digest-pinned remote download, and adding a `t.Skip` when the archive is missing would make the check
silently never run on CI, which weakens the gate. The fix is a design decision for the next round: either give
the gate a bounded offline fetch that verifies `chartSha256` before use, or split this into a
material-required job that runs where the artifact store exists and is *loudly* reported as not-run
otherwise. Recorded as a next action in `docs/execution/progress.yaml`.

Live steps are likewise not reproducible from a clone: they need the three VMs, a built artifact package
and the site configs, none of which is in this branch.
